# 데모 진행 (최종 발표 3분)

대회 규정: 슬라이드 금지, **설계 문서 2분 + 데모 3분**. 목업이 섞이면 목업이라고 밝힌다.
**현재 GCP 프로젝트가 없어 실제 Cloud Run 배포는 미검증이다.** 아래 로컬 배포는 실제로 동작한다. GCP 경로가 준비되기 전에는 클라우드 화면을 실제 클라우드인 것처럼 말하지 않는다.

## 제출용 3분 흐름

| 시간 | 동작 | 증거와 설명 |
|---|---|---|
| 0:00–0:30 | `examples/guestbook`의 Dockerfile·소스(Spillway import 없음)를 보여주고 `python scripts/deploy_webapp.py --target spillway` 실행 | 로컬 소스 → 로컬 DB에 붙인 후보 헬스체크 → 로컬 앱·버스트 이미지 교체 → URL 출력. 실패 시 이전 이미지 복구. 발표 전 한 번 실행해 두면 재배포 경로로 실측 7초(빌드 캐시 적중 시), 첫 배포는 49초 |
| 0:30–0:50 | 출력 URL과 `/healthz`를 연다 | 실제 배포된 웹앱이 응답. 앱 디자인은 평가 대상이 아니라 배포 과정이 핵심 |
| 0:50–1:20 | GCP가 준비됐다면 Cloud Run URL/리비전과 `--target cloudrun --public` 실행 결과를 보여준다 | 공개 URL을 심사위원 기기로 열어 확인. GCP가 없다면 이 부분은 **미구현/미검증**이라고 짧게 말하고 넘어간다 |
| 1:20–3:00 | 방금 배포한 앱으로 아래 상태 전환 데모 중 **장애 대피**를 시연 | 단일 PC Docker면 시뮬레이션임을 명시. 대시보드의 단계별 기록·RTO·유실 건수를 보여준다 |

Cloud Run 이미지 빌드·푸시 시간이 3분을 넘길 수 있으므로, 실제 프로젝트가 생기면 현장에서 리허설해 시간표를 다시 확정한다. `--dry-run`은 실제 배포 증거가 아니다.

## 상태 전환 데모 (하이브리드 런타임)

아래는 대피·버스팅 기능을 따로 보여줄 때의 전체 대본이다. 실제 GCP 구성과 단일 PC 시뮬레이션을 혼동하지 않는다.

## 화면 배치

- 왼쪽: tailnet으로 접속한 관제 대시보드 `http://<CLOUD_TS_IP>:8090` (모드, 트래픽 분담, 인스턴스, 프로브, 단계 기록)
- 오른쪽: 사용자 화면 `PUBLIC_URL` (방명록, 오른쪽 위 배지가 **로컬 서버 / 클라우드**를 표시)
- 심사위원용 QR: `PUBLIC_URL`

## 사전 점검 (발표 10분 전)

1. 모드 **평상**, 데이터 보호 **정상**, 클라우드 인스턴스 **0** (또는 예열 수)
2. `프로브 초기화` 클릭 → 유실 0건, 무응답 0초
3. 부하 입력값: rps **220**, 초 **45** (로컬 한계 약 120 rps의 두 배 가까이)

## Q&A 대비

| 예상 질문 | 답 (근거) |
|---|---|
| 로컬이 죽은 게 아니라 네트워크만 끊기면? (스플릿 브레인) | 트래픽은 엣지로만 들어와서 끊긴 로컬은 요청을 못 받는다. 다시 연결되면 옛 주 DB를 즉시 읽기 전용으로 격리하고, 주 DB 복귀는 재복제 후 계획된 전환으로만 한다. (ADR-07, 대시보드 이벤트 로그) |
| 비동기 복제면 데이터가 날아가지 않나? | 긴급 대피에서는 마지막 몇 건이 이론상 유실될 수 있다. 그래서 프로브로 **실측**해서 보여준다(시뮬레이션 0건). 계획된 이사와 페일백은 쓰기 차단 후 LSN이 같아진 것을 확인하고 전환하므로 RPO 0. 동기 복제 스위치도 있다. (ADR-04) |
| 그냥 처음부터 클라우드 쓰면? | 평소에도 앵커 VM·대기 DB 비용은 발생한다. 대신 버스트 앱은 필요할 때만 띄우고, 주 DB를 사내에 두며 기존 장비를 활용한다. 전체 비용 우위는 실제 클라우드 청구액으로 검증해야 한다. |
| Liqo / Karmada / VMware HCX와 차이는? | 셋 다 K8s 클러스터나 VMware 스택이 전제다. 우리는 노트북 한 대 + Docker. VM이 아니라 앱과 DB를 구분해서, 앱은 서버리스로 늘리고 DB만 복제한다. |
| 전환 시간은 어디서 걸리나? | 대시보드의 단계별 ms 기록. 대부분 장애 감지(헬스체크 2회 + 3초 확인)와 인스턴스 기동. 예열 옵션 `CLOUD_WARM_MIN=1`로 기동 시간을 없앨 수 있다(비용과 트레이드오프, verification-warm.md). |
| 컨트롤 플레인이 대피 도중 재시작되면? | 모드는 DB 역할에서 다시 계산한다. 클라우드 DB가 주 DB면 대피 상태를 복원하고, 작업 기록은 감사 로그 파일에서 되살린다(E2E에서 컨테이너 재시작으로 검증). (ADR-14) |
| 앵커 VM이 죽으면? | 단일 장애점이다. 알고 있는 한계로 문서화했다. (design.md 9장) |
| 여러 사람이 동시에 조작하면? | 컨트롤 플레인이 명령을 한 줄 대기열로 순서대로 처리하고, 변경 API는 토큰으로 보호한다. |
| AI는 어디에 썼나? | 의도적으로 뼈대부터 만들었다. "규칙 몇 줄이면 되잖아?"를 통과하는 자리에만 넣는다. (design.md 8장) |

## 문제가 생기면

- 버스트가 안 일어남 → rps를 올린다(로컬 한계의 2배 이상). `MAX_INFLIGHT`·`WORK_MS`로 로컬 용량을 조절할 수 있다.
- 대피 후 원위치 → **페일백** 버튼 (로컬 복귀가 감지돼야 활성화).
- 완전히 꼬였을 때(시뮬레이션) → `./scripts/sim.sh down && ./scripts/sim.sh up` (약 30초)
