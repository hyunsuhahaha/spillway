# 최종 발표용 한국어 대본 초안 (통역 참고)

현재 버전은 **GCP 프로젝트 없이 진행하는 시연**을 전제로 한다. 실제 클라우드 배포를 검증한 뒤에는 아래의 “미검증” 문장을 지우고 실측 URL·리비전으로 교체해야 한다. 문장 사이에서 통역사가 말할 시간을 준다. 발표는 설계 설명 2분, 데모 3분 안에 리허설한다.

## 설계 문서 설명 — 약 2분

“Spillway는 작은 팀의 로컬 서버를 계속 활용하면서, 트래픽이 몰리거나 서버가 죽었을 때 다른 환경으로 서비스를 이어주는 배포 시스템입니다.”

“문제는 웹앱을 한 번 띄우는 것보다, 환경이 바뀌어도 앱과 데이터가 안전하게 이어지는 것입니다. 기업용 솔루션은 있지만 작은 팀이 쓰기에는 복잡하고 비쌉니다.”

“배포 입구는 로컬 소스의 Dockerfile입니다. 한 명령으로 이미지를 만들고, 후보 컨테이너의 헬스체크를 통과시킨 뒤, 그 이미지를 로컬 앱이자 클라우드 버스트 이미지로 배포합니다. 실패하면 이전 이미지를 복구합니다.”

“배포된 앱은 평소 로컬에서 트래픽을 처리합니다. 과부하 시 같은 이미지의 클라우드 인스턴스가 붙고, 로컬 사이트 장애 시 클라우드 대기 DB를 승격한 뒤 같은 URL로 전환합니다. 앱은 헬스체크, DB 주소 환경변수, 상태 없음이라는 계약만 지키면 됩니다. 실측은 예제 방명록 앱으로 했습니다.”

“현재 한 대 PC의 Docker 시뮬레이션과 자동 테스트는 통과했습니다. 실제 GCP 프로젝트는 아직 없어 Cloud Run 배포와 비용·성능은 실측하지 못했습니다.”

## 실제 데모 — 약 3분

“여기 로컬에서 만든 방명록 웹앱 소스와 Dockerfile이 있습니다. Spillway 코드는 하나도 import하지 않는 평범한 앱입니다. 지금 배포 명령을 실행하겠습니다.”

`python scripts/deploy_webapp.py --target spillway`

“명령이 빌드, 로컬 DB에 붙인 후보 헬스체크, 기존 버전 교체를 수행했습니다. 이제 이 이미지가 로컬 앱이고, 트래픽이 몰리거나 로컬이 죽으면 클라우드에 뜰 이미지이기도 합니다.”

“Cloud Run용 명령 경로도 작성했지만, 프로젝트가 없어서 그 경로는 아직 실제 배포라고 주장하지 않겠습니다.”

“방금 배포한 방명록은 로컬 사이트에서 동작하고, 클라우드 쪽에는 Postgres 대기 복제본이 있습니다. 로컬 사이트의 네트워크를 끊겠습니다.”

`./scripts/sim.sh cut-local`

“대시보드에서 감지, 복제본 승격, DB 라우터 변경, 요청 재개 단계를 확인할 수 있습니다. 사용자 URL은 바뀌지 않았고, 이번 시뮬레이션의 무응답 시간과 유실 건수를 화면에서 확인하겠습니다. 비동기 복제이므로 실제 긴급 대피에서 유실 0건을 보장하지는 않습니다.”

## 통역용 용어

- one action deployment: 원터치 배포
- candidate container: 후보 컨테이너
- readiness / health check: 배포 준비 상태 / 헬스체크
- burst capacity: 부하 시 추가 앱 용량
- failover / failback: 장애 대피 / 원위치 복귀
- standby replica: 대기 복제본
- RTO / RPO: 서비스 복구 시간 / 데이터 복구 지점 목표
- split brain: 두 DB가 동시에 주 DB처럼 쓰기를 받는 상태
